# @xihan-ui/markdown

流式 Markdown 渲染内核：喂截至当前的全文，拿回一组带稳定 key 的已渲染块（零第三方运行时依赖）。

- 对外只有一个工厂 `createStreamRenderer()`。解析、切块、冻结缓存一概不暴露——中间态放出去，
  消费方迟早绕过缓存直接改块，增量渲染的保证就没了。
- 生长中的那一块 key 恒为 `LIVE_BLOCK_KEY`，定型块由下标与内容摘要拼成。key 稳定是防整段重建的关键：
  每帧换 key 的话，用户每收到一个 token 就要被重建一次节点，选区和滚动位置全丢。
- 消毒收在解析器内部：`html:false` + 协议白名单，而不是渲染后再过一道清洗。

## 这是一个子集，不是 CommonMark 实现

**当前对官方 652 条用例的一致率：392/652（60.1%）**，逐节数字见
[`tests/commonmark-baseline.json`](./tests/commonmark-baseline.json)。

这个数字不是目标，是**事实的记录**。本包服务的是 AI 聊天输出，不是通用 Markdown 渲染，
所以不追求满分；但一致率必须是可核对的数字而不是一句形容词——手写用例只能证明
"想到的都对"，证不出"没想到的偏了多少"。

### 按设计不打算过的

| 节 | 条数 | 原因 |
| --- | --- | --- |
| HTML blocks | 0/44 | 原生 HTML 块不透传 |
| Raw HTML | 5/20 | 行内原生 HTML 不透传 |

这是消毒面收在解析器内部的代价，也是本包最重要的一条安全约束，不会为了跑分改掉。
把这两节摘掉之后的一致率是 392/588（66.7%）。

### 已知缺口（想修的话从这儿看起）

| 缺口 | 波及 | 说明 |
| --- | --- | --- |
| 缩进代码块未实现 | `Tabs` 0/11、`Indented code blocks` 1/12，并污染列表与引用块 | 四空格 / tab 起始的块落成了段落。对聊天场景这未必是缺陷——随手缩进的正文被当成代码同样难受，要不要实现是个产品选择 |
| 列表里的空行与延续内容归属 | `List items` 12/48、`Lists` 6/26 | 连续两个空行会把一个 loose list 切成两个；缩进的延续段落没并进列表项。这是眼下最大的一块 |
| Setext 标题 | `Setext headings` 11/27 | 段落下面一行 `---` 现在按分隔线处理，没有回头把上一段升成标题 |
| 链接引用定义 | `Link reference definitions` 11/27 | 定义的收集与消费只覆盖了常见形态 |
| `<li>` 内换行位置 | `List items` 等 | 纯序列化差异（`<li>\n<p>` 与 `<li><p>` 语义相同），混在失败数里，修列表时会一并变化 |

## 一致率棘轮

`tests/commonmark-spec.spec.ts` 逐节比对通过数与基线，**要求逐字相等**：

- 掉了 → 回归，测试会指出是哪一节掉的；
- 涨了 → 好事，但基线得跟着重记，否则棘轮就松了。

一节一记而不是记个总数，是为了让"这边修好两条、那边悄悄坏掉两条"露出来。

官方用例来自 devDependency [`commonmark-spec`](https://www.npmjs.com/package/commonmark-spec)
（CC-BY-SA-4.0，CommonMark 0.31.2），只在测试期读取，**不进产物**。

重记基线：改完解析器后跑一次测试，红字里会写出每节的实际值，照着改
`tests/commonmark-baseline.json` 即可。
