# Accessibility and keyboard

In XiHan.UI accessibility is a criterion: every component has a machine-readable keyboard specification, and it doubles as the test denominator.

## Keyboard specifications

```ts
export const accordionKeyboard: KeyboardTable = {
  component: "accordion",
  source: "https://www.w3.org/WAI/ARIA/apg/patterns/accordion/#keyboardinteraction",
  rows: [
    {
      id: "accordion.kbd.toggle",
      keys: ["Space", "Enter"],
      when: "focus in trigger, not disabled",
      does: "expand / collapse the content of this item",
    },
    {
      id: "accordion.kbd.next",
      keys: ["ArrowDown", "ArrowRight"],
      when: "focus in trigger, key on the orientation axis (left and right swap under dir=rtl)",
      does: "move focus to the next trigger, without wrapping at the last item",
    },
    // …
  ],
};
```

Every row has a stable `id`, the trigger keys, a precondition and an effect. Each component has its own table.

The specification is consumed by three parties:

1. Tests: conformance cases point back to row ids through their `covers` field, and a suite missing one row fails;
2. Documentation: the keyboard table of every component in the [component reference](../components/) is rendered from it;
3. Review: the `source` field points at the origin of the specification (a W3C APG pattern, WAI-ARIA, the HTML standard or a WCAG technique), so behavior changes can be traced back to their basis.

::: tip An external denominator
Making keyboard tests pass can only be done by writing cases, never by changing the denominator. The specification is a contract established up front, not a record added afterwards.
:::

## Deliberate choices about ARIA

These treatments appear again and again in the component sources, and each is a considered trade-off:

- `aria-disabled` instead of `disabled` when a disabled item must stay focusable. Native `disabled` removes the element from focus, so screen reader users can neither Tab to it nor hear why it is unavailable. Disabled accordion items and loading buttons work this way.
- No roving tabindex where it does not belong: every accordion trigger is its own Tab stop, as the APG prescribes for that pattern. Components not outputting `tabindex` there is intentional.
- Arrow key axes and writing direction: vertical lists ignore left and right; under RTL, left and right swap meaning. Both rules live in one place, `navIntentFromKey`, shared by every list-like component.
- Keys not handled by navigation are not `preventDefault`-ed; otherwise they would swallow input methods, browser shortcuts and default behavior.
- No misreading during IME composition: `isComposingEvent()` recognizes keys pressed while composing, so the `Enter` that confirms a candidate is not taken as a submit.

## Background inertness and focus

A modal overlay is assembled in a fixed order when it opens:

1. Register the layer and push it onto the layer stack;
2. Set up dismissal (Esc, outside clicks, focus leaving);
3. Set up the focus scope (trapping, wrapping, restoring);
4. Lock scrolling;
5. After the host commits the overlay nodes, add `aria-hidden` to the background; layers without a backdrop also get a transparent plate inside the positioning layer that blocks the pointer.

The order cannot be swapped.

## Visible focus

The focus ring is drawn by one common skin shared by the whole library: width `--xh-ring-width`, color `--xh-_ring-color` (default `--xh-ring-focus`) and offset `--xh-ring-offset`. The offset is minus one ring width: the ring is drawn inward, its outer edge coincides with the outer edge of the element's border, and the element takes the same space before and after focus without pushing its surroundings.

WCAG 2.2 non-text contrast (SC 1.4.11) asks for at least 3:1 between the focus indicator and the adjacent colors. With the ring drawn inward, two colors are adjacent:

- Inside: the element's own face. This is the basis of the judgment.
- Outside: the background the element sits on. It changes with wherever the component is placed, the library cannot decide it, so it is measured but not judged.

### `currentColor` rings on solid faces

On solid faces (solid buttons, the track of a checked switch, a selected calendar cell, a slider being dragged and so on), the ring color belongs to the same family as the face, and the contrast can drop to 1.00:1. In those states the skins set the ring color slot to `currentColor` in their `:focus-visible` rules, so the ring takes the foreground color paired with the face. That foreground already has to keep text readable on the face (4.5:1 on the solid background), so as a ring color it naturally exceeds 3:1.

A ring color change is judged by evaluation, not by literal text: assigning `--xh-_ring-color` or `outline-color`, or writing an `outline` shorthand in a keyboard focus rule, counts as changing the ring color when the value — expanded through the slots of the skin and resolved through the token chain to a color — differs from both library rings (`--xh-ring-focus` and `--xh-ring-invalid`) in any theme × tone. Values that cannot be resolved (`currentColor`, colors passed in by users, user tokens without a fallback) count as changes too. So writing a foreground token paired with the face, such as `var(--xh-fg-on-brand)` (the track of a checked switch does this: it is a `<button>` and the skin gives it no `color`), is constrained the same way as `currentColor`, while writing back `var(--xh-ring-focus)` is not a change. Writing `outline-color` directly, uppercasing the property name, wrapping the rule in `@supports` or in conditional blocks whose falsity cannot be decided statically such as `@media screen` / `@container`, writing it under a bare `:focus`, and covering several states with attribute-existence selectors such as `[data-variant]` / `[data-state]` are all within scope. The two library ring tokens and the names on their resolution chain (such as `--xh-color-brand-500`) may never be assigned inside skins: changing them on a subtree means the library ring is no longer the library ring on that subtree.

::: warning This is not the ring following the tone
Four rules have to be read together:

- The ring does not follow the tone: `data-tone` switches the color family, and the ring does not switch with it. The tone colors themselves do not reach 3:1 as ring colors (warning is 2.70:1 on white, success 3.04:1). States without a solid face always use `--xh-ring-focus`.
- `currentColor` on solid faces: it takes the foreground paired with the face, not the tone color. On the same danger solid background, the ring is the text color on that background, not danger itself.
- Tinted states that already pass do not change the ring for uniformity: tinted and transparent faces use the default ring (from 3.40:1); switching them to `currentColor` would turn a brand ring into near black or near white and diverge from the rest of the family. `currentColor` is only used on solid states, and the selector granularity matches the granularity of the face.
- Disabled states are exempt from contrast, but the ring may not disappear: WCAG 1.4.11 does not ask disabled controls for 3:1, and the library does not chase that number; but `color: transparent`, or grayed text with the same color as a grayed face, makes a `currentColor` ring completely invisible. That is not low contrast but no focus indication at all. Such states either fall back to the default ring or get a separately paired foreground.

The criterion is the face under the ring, not the component's tone.
:::

### Whether overlay shells take focus

Most overlay panels are only fallback landing spots of the focus trap (`tabindex=-1`); the ring sits on the controls inside, and the skins turn off the panel's own ring and register who draws it in the `ringless` section. The tour bubble is the exception: Enter / Space on it advances to the next step, which makes it an actionable target (WCAG 2.4.7) that needs visible focus. After programmatic focus it uses the default inward ring; its face is `--xh-bg-surface`, and the default ring passes. The browser criterion `focus-ring-inset-grpring` guarantees this.

### Field shells do not draw a ring

Field shells such as the input shell and the InputGroup shell draw no focus ring when focused: the shell stroke switches to `--xh-border-control-focus` (the same color as `--xh-ring-focus`, at least 3:1 against the canvas, faces and tints), and the background switches from the field tint `--xh-bg-field` to the carrying surface `--xh-bg-surface`. Focus is shown through two channels, the stroke color and the background difference; forced colors add a `Highlight` ring. Search boxes embedded in panels (the search of Command, Cascader, TreeSelect, Transfer and SideNav) have no shell, and the caret is the focus indicator when they are focused. These places are registered in the `ringless` section of the focus ring gate.

### Related criteria

| Criterion | What it checks |
| --- | --- |
| `check-focus-ring` | The ring's width, color or offset is written as a literal instead of a token, so themes and global adjustments cannot reach it |
| `check-focus-ring-surface` | Statically resolves the face and ring color of every focusable state, and fails states whose face is below 3:1 against the ring without a ring color change. Ring color changes (`--xh-_ring-color` / `outline-color` / an `outline` shorthand in a focus rule, evaluating outside the library rings) that reach non-solid states, `:focus-visible` rules that turn the ring off (`outline: none` / `outline-width: 0`) without registration, and solid faces that take no focus without registration fail as well; a focus rule that makes the ring transparent fails outright, with no registry. Rules inside `@supports` blocks are treated as applying; for `@media`, only real media conditions (print, high contrast, reduced motion, coarse pointer, breakpoints) count as conditional blocks, while other forms (`screen` / `all` / comma lists / `not`) and every `@container` are treated as applying. Attributes a rule writes without a value count as covering in existence form; with a value, it depends on whether a sibling state claims it |
| `check-focus-outline-reset` | A skin resets `outline` (including `outline-style` / `outline-width` / `outline-color`) under `:focus:not(:focus-visible)`. The UA only draws the ring under `:focus-visible`, so that reset is dead code, and the `outline` shorthand resets `outline-color` to `currentColor`: once the stroke color is transitioned, a near-black stroke flashes when focus leaves |
| `focus-ring-inset-grpring` | Browser state: the inward ring keeps the same footprint before and after focus, and the library has only one offset; every rule that changes the ring color (likewise judged by evaluation; `@media` follows the media environment of the current page, `@container` is handled normally) is focused and measured for 3:1 one by one; the tour bubble shows a ring when focused |
| `focus-ring-face-contrast` | Browser state: derives the states from the skins and measures the actual contrast between ring and face state by state in real Chromium |
| `focus-ring-disabled-ink` | Browser state: disabled states use the default ring instead of the grayed foreground; non-disabled solid states still take their own face's foreground |

`focus-ring-face-contrast` only measures faces the library paints: parts whose skin paints no face, and whose computed background equals the UA background of a bare element of the same tag (a menu trigger only paints its expanded state; the base state shows the `buttonface` of a native `button`), are not in the state table, because the color inside the ring is not the library's. States that clearly fail and cannot be fixed by changing the ring color are registered in `KNOWN` and checked both ways: the state can no longer be mounted, the state no longer draws a ring, or it now reaches 3:1 — any of the three marks the registration as stale.

The denominators of the two criteria are reconciled with each other. Every solid state computed statically must be mountable in the browser, measure as solid there, and agree on whether the ring is revoked; every solid state measured in the browser must either be computed statically as the same face (the same key, or a state covering it, with the same ratio) or be explained in the `declared` section of the registry as to why it cannot be computed. Keys on both sides are normalized into one form before comparison (`:is()` expanded, ancestors that only write root removed); combinations that stack into the same face are measured once, and aliases lead to the state already measured. Mismatches are registered one by one with reasons in `focus-ring-face-contrast.reconcile.json`; registered entries must still mismatch, and mismatches must be registered.

The static and browser criteria each have blind spots, which is why both are kept. The static one is fast and can compute states that only appear after interaction (`[data-dragging]`, `[data-state='picking']`), but cannot see faces painted on ancestors, a ring color change whose `color` is replaced by another rule, or a later rule in the same state writing the ring color back to default — the stacking of the cascade. The browser one measures actual values and covers more, but cannot measure focus combined with `:hover` / `:active` (moving a real pointer makes the browser leave keyboard modality, and `:focus-visible` disappears at once), and backgrounds laid by `::before`, faces under real media conditions and faces inlined into `style` by the connect layer (the swatches of the color picker, the image of the cropper) are out of its range.

## Automated scans in the browser

The fixtures of the conformance suite are mounted in real Chromium, and axe runs on the initial state and the end state of every case. End states are deduplicated by their shape signature, so the same shape is not scanned twice.

Every fixture runs once with a light and once with a dark `data-theme` on the root, with `bg-canvas` / `fg-default` laid on the body as the base: when axe finds no ancestor painting a background it assumes white, and a dark run without a body background would compare dark text against white.

This has to run in a real browser: jsdom has no layout, so contrast, target size, flipping and collision avoidance cannot show up.

```bash
pnpm exec playwright install chromium # first time only
pnpm test:browser
```

## The registry of known violations

Known issues found by the scans are registered in `tooling/testing/src/a11y/known.ts`. A hit on a registered rule does not fail, but a registration that no longer hits anything is stale: after a fix it must be removed from the table, so no exemption outlives its reason.

There are six entries today. Five are shared by the three adapters: the disabled label text of `tag` uses the library-wide `fg-disabled` / `bg-muted` (2.36:1 in light, 1.93:1 in dark), which is exempt as a disabled control under 1.4.3, but the tag root has no disabled semantics axe recognizes, so it gets flagged; the removable tags of `select` outside the trigger are in the same position (tags inside the trigger sit in a natively disabled button that axe skips; the outer ones are role-less spans); the tag row of `combobox` comes before the input and is not inside any natively disabled control, so its disabled tag text belongs to the same case; when `file-upload` is disabled, the names and sizes of the file items also take `fg-disabled` (2.58:1 in light, 2.27:1 in dark) — the items are `role=listitem` and cannot carry `aria-disabled`, the three buttons are natively disabled and skipped by axe, so only these two texts are flagged; the input of `prompt-input` deliberately does not emit an unconditional `aria-label` (it would override the author's `<label for>`), and the conformance fixture deliberately provides no text to protect that contract, so the scan sees a textarea without a name, which authors name in real use. One belongs to the Web Components adapter alone: the required children of `steps` are written by the author and may lack the direct children their role requires. The global registry is empty. Registrations are kept per theme: hits in both the light and the dark run go into the shared table, hits in only one theme go into `knownByTheme`, both sides have stale checks, and a registration that is no longer found fails as well.

::: warning
This table is a faithful record of the current state, not a statement that it is acceptable. While it still has entries, assess the impact on your compliance requirements yourself.
:::

## Exemption from step replay

Only one component cannot be driven to the end state of its cases in a real browser, and both adapters share the registration:

- `breadcrumb`: the scan has to block cross-document navigation, otherwise the test host navigates away; yet the cases assert exactly that it is not blocked, and both cannot hold within one document.
